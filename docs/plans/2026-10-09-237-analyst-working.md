## Decision log

| Question | Taken | Why |
|---|---|---|
| The Target screen's report wait too | Yes, the same component | The issue's "why" is the finals' step 4: "a run set and its report live on the judges' app". That report is written from the Target screen (`docs/DEMO.md`, "The flow", step 4; `target-view.tsx`, "the report is written from here"), whose wait shows a static line today. Doing only the Report would leave the finals' own wait as it is |
| The lines | The issue's eight, the last reworded (review) | Each reads as an activity under way, none as a stage done, none holds a number or a persona's name, and none uses "Words we do not use". The test turns away digits, percentages, a few stage words, persona names and the banned words; it is a denylist, so the rest is for whoever edits the list. The last line read "A careful report takes a minute.", which a clock reading 4:10 beside it would disprove, so it reads "takes its time." |
| How the line is chosen | From the elapsed time: line `floor(t / 4 s) mod 8` | One clock drives both the time and the line, so there is no second timer and no state to drift; the same time always shows the same line |
| Where the time starts | The analysis's `submittedAt`, on both screens (see the build row below) | The Report can be opened while an analysis started on an earlier visit runs; its mutation's `submittedAt` is the real start. The Target screen reads the same mutation |
| The tick | Once a second, while mounted | The time reads seconds. Nothing animates: the text is replaced, as the issue asks |
| Reduced motion | The list's first line, fixed; the time still counts | The issue: "posts still, one fixed line". The time is a number changing, not motion, and it is what tells a person the page is alive |
| The status region | Always mounted, `sr-only`, holding the start line while running and "The report is ready." once done; the changing line and time sit outside any announcement | A region mounted with its text already in it is often not read; one that changes its text is. The visible posts and lines are the sighted reading of the same state |
| A failed analysis | The fault banner, as today | It is `role="alert"` already, so it is announced once; the status region goes quiet |
| Where the Target screen takes the start | `target.tsx` passes the report mutation's `submittedAt` to the view as `ReportState.since`, not the component's mount (build) | The Target screen reads the same `["analyse", taskId]` mutation as the Report, so a report asked for on the Report screen or an earlier visit shows here too; its real start is the mutation's. This touches `target.tsx`, which the plan did not list |
| The Target screen's changing line | Under the status region, outside it, not inside it with a nested `aria-live="off"` (review) | `role="status"` is atomic, and a nested `off` is honoured unevenly by browsers and screen readers, so a line inside could be read out every second. Outside, it matches the Report |
| Reduced motion | Read during render, not through a subscription (review) | The component renders every second for its clock, so a change of the setting shows within a second; the subscription was 13 lines for nothing |
| One read of the analysis for both screens | `analysisKey` and `useAnalysis` in `api/reports.ts`, used by the Report, the Target screen and `reportMutation` (simplify) | Both screens read the same mutation, each with its own key, select and `.at(-1)`; one hook and one key keep them in step, with one cache subscription each instead of two |
