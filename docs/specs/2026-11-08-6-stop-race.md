# #6 — Stop a race from the Race screen: spec

Task: issue [CShark-Hub/wayford#6](https://github.com/CShark-Hub/wayford/issues/6), "Stop a race from the Race screen", slice 1 of the issue's two ("Possible slicing"), so the PR is `Part of #6`. The whole issue is larger than L: four packages, two contracts in `packages/core`, a dialog and an agent change. Slice 1 is at the top of L: it changes `RunEvent` and `RunResult` through the outcome lists, adds a record to `Race`, and touches about thirty files across core, io, agent, web and the docs, most by a few lines · Branch: `feature/6-stop-race` · Date: 2026-11-08
Status: draft

## Goal

From the Race screen, a person stops a race's runs that are still waiting for a slot: after a confirmation they never start, their lanes read Stopped, and they count nowhere. The runs already under way finish as today; stopping those is slice 2.

## Constraints that bind

- Slice 1 is "The core outcome, cancelling queued runs in io, and the UI button and dialog. No agent change" (issue, "Possible slicing"). The issue comment of 2026-11-08 adds: "Running runs finish as today, and the dialog says so", and the button goes in `TooManyToFollow` too.
- Out of scope (issue): stopping every running race at once; sweep runs, "which belong to no race"; aborting the in-flight LLM request; "A stored record for a run dropped from the queue: it never started, so there is nothing to store. Box 3 covers runs stopped while running."
- "A cancelled run is **not a result** (`AGENTS.md`, 'Seed'): it never counts in k/n, the Analyst or a sweep. A distinct outcome keeps that a one-line filter; reusing `runFailed` would read as a crash and pollute the error count" (issue, "core").
- "The race records `cancelledAt` rather than a third `RaceStatus`, to keep contract churn small" (issue). A race "holds no status: whether it still runs is io's runner's to say, at read time" (`packages/core/src/race.ts`, header).
- `POST /races/:id/cancel`, idempotent: `202 { stopped, dequeued }`, `200` with zero counts on a race already finished, `404` on an unknown race, keyed on `raceId` so it works after a reload or from another tab (issue, "io").
- The button: "Quiet destructive style, not primary"; "Keep running" has default focus; Esc dismisses; "Reuse the settings dialog's primitive (s3-19)"; after confirming it reads "Stopping…" and is disabled; a stopped lane is neutral, "not failure red"; the k/n line leaves stopped runs out, as in "1/2 got through, 3 stopped" (issue, "web").
- The seven contracts in `packages/core` are frozen and outrank new shapes. A field added to a stored record is optional, so records stored before it still parse (s2-09's spec). New shape, new fixture, same PR, and each schema keeps one full fixture (`docs/CONVENTIONS.md`, "Tests"; `docs/PLAN.md`, the seven contracts).
- Six avatar states, driven by run events (`docs/PLAN.md` F6 AC2 and the UI section). DESIGN.md: outcomes are fixed words; fault is for "System failures only"; one ink primary per view; Button has default, outline and ghost, and no destructive variant; nothing animates but colour and opacity.
- io keeps importing agent as types only (`packages/io/src/index.test.ts`). `Date.now()` never influences a decision, only timestamps (`docs/CONVENTIONS.md`, "Determinism rules"). No new dependency without a `docs/STACK.md` line.
- Three lanes and the header fit 1280 × 720 with no scroll (`packages/web/scripts/self-check.browser.test.ts`, the fit tests), and check:self passes on `/race` (issue, box 6).

## Design

### Data flow

1. io answers every race with `waiting`: the ids of its runs still waiting for a slot, read off the runner per request, like `status`.
2. The Race screen shows "Stop race" while the race is not over and a run is waiting. The button opens a confirmation. "Keep running" and Esc close it and send nothing.
3. "Stop race" in the dialog sends `POST /api/races/:id/cancel` with the body `{}`. io loads the race, has the runner drop each of its runs still waiting, writes the stop into the race's record, and answers `202 { stopped: 0, dequeued: n }`.
4. Each dropped run never starts. Its stream ends at once with one `runFinished` whose outcome is `cancelled`, and nothing is stored. The live lanes read it and draw the run Stopped. The k/n line leaves it out.
5. A race opened again after io restarted is drawn from its records. The stop record names the dropped runs, so they are drawn Stopped and not as lost streams.

### core: the outcome (`packages/core/src/run.ts`)

```ts
export const RUN_OUTCOMES = ["success", "gave_up", "budget_exceeded", "error", "cancelled"] as const;
export const FINISHED_OUTCOMES = ["success", "gave_up", "budget_exceeded", "cancelled"] as const;
```

- `cancelled` is appended last, so every list that prints the outcomes in order keeps its prefix. It joins both lists: `FINISHED_OUTCOMES` stays a subset of `RUN_OUTCOMES`, which the fold (`outcome: terminal.type === "runFailed" ? "error" : terminal.outcome`) and web's `RunView` rely on. Slice 2 stores cancelled runs, so `RunResult` needs it anyway.
- `RUN_OUTCOMES`' doc comment gains `cancelled`: a person stopped the run's race (#6). It is not a result, so it never counts in k/n, the Analyst or a sweep. Today io gives it only to a run it dropped from the queue before it started. That run's stream is the one `runFinished`, which never folds into a record, because a stream must open with `runStarted`.
- `FINISHED_OUTCOMES`' doc: "The ways a run finishes without crashing". The fold's doc gains one line on the dropped run's lone `runFinished`, which io never folds.
- `RunResult`'s last-step checks stay as they are. A cancelled run may not end on a wasted or incomplete step, the same rule as `success` and `gave_up`. No cancelled run is folded in slice 1, and slice 2, which stops a run at the step boundary, decides whether that changes.

### core: the stop record (`packages/core/src/race.ts`)

```ts
/**
 * A stop of the race (#6): `at` is when the first stop that dropped a run was confirmed, a
 * timestamp, never a decision; `dequeued` are the runs it dropped from io's queue before they
 * started, in queue order. A run listed here never started and is never stored.
 */
export const RaceCancel = z.object({ at: z.iso.datetime(), dequeued: z.array(RunId).min(1) }).strict();
export type RaceCancel = z.infer<typeof RaceCancel>;

export const Race = z
  .object({ id: RaceId, task: Task, startedAt: z.iso.datetime(), runs: z.array(StartedRun).min(1), cancelled: RaceCancel.optional() })
  .strict()
  .superRefine(/* every id in cancelled.dequeued is one of runs' ids, and none twice */);
```

- One optional object, not a flat `cancelledAt` beside a list. The two always come together, the precedent is `RunResult.sweep`, and a race stored before this parses unchanged.
- The ids have to be stored, not counted. A finished race is drawn from its runs' records, a dropped run has none, and after a restart the runner's memory is gone.
- `RaceStatus` does not change. web's `Race = StoredRace.extend({ … })` keeps the refine: zod's `extend` keeps checks when it adds keys.
- The fixture `race.json` becomes a full one. A fourth run, Milo on seed 1, comes last, and `cancelled` names it. `race.test.ts`'s first test then compares the runs the race kept, all but `dequeued`, with those its report cites for seed 1. Only core's `race.test.ts` and io's `db/races.test.ts` read the fixture.

### io: the runner (`packages/io/src/runner.ts`)

```ts
export interface Runner {
  start(…): StartedRun[];
  live(id: string): LiveRun | undefined;
  /** Whether `id` is a run of this process still waiting for a slot. */
  waiting(id: string): boolean;
  /**
   * Drops each of `ids` still waiting for a slot (#6): it never starts, its stream ends with one
   * `runFinished` `cancelled`, and nothing is stored. Returns the ids dropped, in queue order. A run
   * that holds a slot, has ended or is unknown is left as it is. Synchronous, so no run can take a
   * slot between the check and the drop.
   */
  cancel(ids: readonly string[]): RunId[];
}
```

- The slot queue keys its waiters by run id. `take(id): Promise<boolean>` resolves `true` when the run gets a slot, and `false` when it is dropped. `drop(ids)` takes the waiters out and settles each with `false`, without touching the count of open slots, since a waiter never held one. `has(id)` answers `waiting`.
- `job` returns at once when its `await slot` answers `false`. It never reads the step cap, never calls `run`, and never calls `slots.free()`.
- `cancel` ends each dropped run's live stream itself, at drop time, with `RunEvent.parse({ type: "runFinished", runId, stepIndex: 0, timestamp, outcome: "cancelled", durationMs: 0, cost: NO_COST })`. The values are `ownFailure`'s for a run that never started. It does not go through `closeOut`, which would log an error and publish `runFailed`. The `lives` entry stays, ended:
  - `GET /runs/:id/events` replays the one event;
  - `raceStatus` reads the run as ended;
  - a race whose runs have all ended or been dropped reads `finished`.
- `lives` holds the writers (`LiveWriter`), so `cancel` can end a stream. `live(id)` still hands out the reader.
- The header's account of a run's life gains the drop. "A set cut short still has whole seeds" holds for a set io cuts short, not for one a person stops: a stop drops the tail of the queue, which can end mid-seed.

### io: the routes (`packages/io/src/routes/races.ts`, `packages/io/src/db/races.ts`)

- `GET /races` and `GET /races/:id` answer `{ ...race, status, waiting }`. `waiting` is `race.runs` filtered by `runner.waiting`, so a race from an earlier process lists none.
- `POST /races/:id/cancel` takes the strict body `{}`, as `POST /tasks/:id/scout` does. io answers 415 to a POST without `application/json`, and web's `postJson` always sends JSON. Its steps run synchronously after the body is read:
  1. `loadRace`. If io keeps no such race, including a malformed id as `GET /races/:id` treats one, it answers `404 { error: "no race <id>" }`.
  2. If `raceStatus` reads `finished`, it answers `200 { stopped: 0, dequeued: 0 }` and writes nothing. The issue calls this case a no-op, and it covers a race from before an io restart.
  3. Otherwise `runner.cancel(race.runs ids)`. When that dropped any run, io writes the stop with `updateRace` (`at` is the first stop's, and `dequeued` grows by the new ids) and logs one info line, "race stopped", with the race id and the count. It answers `202 { stopped: 0, dequeued: <dropped> }`.
- A second stop finds nothing waiting. It answers `202 { stopped: 0, dequeued: 0 }` while runs still finish, then `200` once the race has finished. Either way the first record stays as it was. That is the idempotence the issue asks for.
- `stopped` counts the runs under way that the stop will end, which is slice 2's work, so it is 0 in slice 1. The field is there now, so the answer keeps its shape.
- `updateRace(db, race)` (new, in `db/races.ts`) replaces a stored race's document, parsed with `Race` on the way in, as `saveRace` does. `saveRace` still inserts once.
- `RacesRouteOptions` names `logger`, which `createApp` already spreads into it. The routes' header, and the "Nothing here writes" comment, now say that the stop is the one write.
- `routes/runs.ts`'s docs gain a dropped run. Its `GET /runs/:id` is a 404 for good. Its stream's terminal event comes at once, with no save tried.

### agent (`packages/agent/src/calibration.ts`)

`calibration.ts` returns `result.outcome` into its own `End` type, so typecheck forces a line for `cancelled`. A calibration run is never in a race, so it can never be stopped. That line is a built-in `Error` only a bug can reach (`docs/CONVENTIONS.md`, "Errors"). No other agent code changes.

### web: reading io (`packages/web/src/api/races.ts`)

- `Race = StoredRace.extend({ status: RaceStatus, waiting: z.array(RunId) })`.
- `RaceStop = z.object({ stopped: z.number().int().nonnegative(), dequeued: z.number().int().nonnegative() }).strict()`.
- `cancelRace(id): Promise<RaceStop>` posts `{}` to `/races/<id>/cancel` and parses the answer. Every race answer in the web's tests, self-check and browser fixtures gains `waiting`.

### web: the outcome and the lane

- `components/outcome-words.ts`: `cancelled` reads **Stopped**. The internal name differs from the word, as with `gave_up` and `budget_exceeded`.
- `components/outcome.tsx` gets a new `OutcomeKind`, `stopped`:
  - its word is "Stopped" and its tone neutral (`text-ink-2`, as Gave up);
  - its glyph is a small filled square, the stop sign, drawn like the others;
  - `KIND_OF.cancelled` is `stopped`.

  It is an ending, since the run will never run again. So the lane is raised as a finished race lane, its end mark is the square, and its track word reads "stopped". The glyph and the word say it, never the colour alone.
- `arena/avatar-state.ts`: a `cancelled` `runFinished` leaves the state `idle`, since the run never moved. Today every outcome other than success becomes `gaveUp`, which is the persona's own decision and wrong here. The six states stay. `RaceView`'s `LaneOf` draws a stopped lane's avatar dimmed with no state, as it draws a lost lane's: the tile decides, as in s3-03.
- `arena/race-view.tsx`:
  - `detailOf` gives a cancelled run the line "Never started: it was still waiting for a slot".
  - The k/n line counts n over the runs that were not stopped. It adds ", N stopped" before any ", N streams lost". When every run was stopped it reads "N stopped" alone, not "0/0".
  - The finish order, which a screen reader hears, lists a stopped run among the runs that did not get through, with its word.
- `arena/race.ts`:
  - `ENDED_STATES.cancelled` is `idle`.
  - `STOPPED_LANE` is the fold of a run the stop record names: Stopped, "0 steps", no pips, not lost, not stored, with the detail above.
  - `stillWaiting(waiting, snapshot)` gives the runs io listed as waiting when the screen asked, less those whose stream has brought any event since.
  - `underWay(runs, waiting, snapshot)` gives the runs neither waiting, nor ended, nor lost.
  - The doc comments that say io cannot cancel now say what a stop does.

### web: the button and the dialog (`packages/web/src/arena/stop-race.tsx`, new)

- `StopRace({ waiting, running, pending, onConfirm })` is built on Radix `AlertDialog`, from `radix-ui`. That is the settings dialog's `Dialog` with `role="alertdialog"` and focus on its Cancel, so it adds no dependency. It reuses the settings dialog's overlay and content classes, with no animation classes.
- The trigger is "Stop race", an outline `Button`, like New race: quiet, not primary, never fault. While `pending` it reads "Stopping…" and is unavailable.
- The content:
  - Title "Stop this race?".
  - A Description, so the dialog has `aria-describedby`, from `StopRaceBody`, which is pure.
  - The buttons, in this order: "Keep running" (`AlertDialog.Cancel`, outline, focused on open) and "Stop race" (`AlertDialog.Action`, the dialog's one ink primary, which calls `onConfirm`).
  - Esc and "Keep running" close the dialog and call nothing. A click outside does nothing.
- `StopRaceBody({ waiting, running })` is pure, so a static test reads it. Radix's `Portal` renders nothing in a static render. Its copy, with counts when they are known (the lanes view):
  - "2 runs still waiting for a slot won't start."
  - "3 runs already under way finish, and their results count." This sentence is left out when no run is under way.
  - "A stopped run never counts toward results."

  Without counts (`TooManyToFollow`, which follows no stream): "Runs still waiting for a slot won't start. Runs already under way finish, and their results count. A stopped run never counts toward results."

### web: the screens (`packages/web/src/screens/arena.tsx`, `packages/web/src/arena/race-view.tsx`)

- `RaceView` takes an optional `stop: { waiting: number; running: number; pending: boolean; error: string | undefined; onConfirm: () => void }`.
  - When `stop` is given, the race is not over, and `stop.waiting > 0`, `StopRace` sits after New race.
  - When `stop.error` is set, a line under the buttons reads, in fault: "io did not stop the race: <message>. The race keeps running." It is a `role="alert"` line, as the start panel's is.
  - `RaceView` stays pure. The mutation lives in `arena.tsx`, since `RaceView`'s tests have no `QueryClient`. `StoredRace` passes no `stop`.
- `LiveRace` holds `useMutation({ mutationFn: () => cancelRace(race.id) })`. It passes `stop` with `stillWaiting(race.waiting, snapshot).length` and `underWay(…).length`. The dropped runs' terminal events reach the lanes through their streams, so nothing is refetched. Once nothing waits, the button goes.
- `TooManyToFollow` holds the same mutation. Below its paragraph, beside New race:
  - **Stopped earlier** (the race has `cancelled`): the line "Stopped: N runs never started. The runs under way finish." No button, since nothing waits after a stop.
  - **Stop answered**: the line "Stopped: N runs waiting for a slot won't start. The runs under way finish." When `dequeued` was 0: "No run was still waiting for a slot: the runs under way finish."
  - **Otherwise, when `race.waiting` is not empty**: `StopRace` with no counts, and the fault line on a failed request.
- `StoredRace` asks io only for the records of runs the stop record does not name, and draws those runs as `STOPPED_LANE`. Asking for them would only bring 404s, and the lanes would read "Stream lost" in fault.
- The note under New race, "A new race queues its runs behind these", stays as it is. In slice 1 a stop leaves the runs under way running, so a new race still queues behind them. The issue's offer to stop in that note belongs with slice 2, when Stop shows whenever the race runs.
