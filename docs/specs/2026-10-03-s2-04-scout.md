# s2-04 — Scout: ground truth per task: spec

Task: `tasks/s2-04-scout.md` · Branch: `feature/s2-04-scout` · Date: 2026-10-03
Status: approved 2026-10-03

## Goal

For each task, an unconstrained run with full vision records whether the goal is reachable, the path it took and the target element. Then the report can tell "the feature is broken" from "the feature works but Vera could not find it".

## Constraints that bind

- "Scout is mandatory … ground truth (where the target actually is, minimum path length)". "**The Actor has no access to Scout's output.**" (`AGENTS.md`). F4 AC3: a test fails if the import appears.
- Full vision: no thresholds, no caps, every pattern known, no behaviour dice. Model role `scout`. Up to 3 attempts. The shortest success is the ground truth, every success is kept with its path, and no success is a result too (task, Constraints).
- Scout's model id goes on the `GroundTruth`. The PR says either that attempts emit no `runStarted`, or that they are runs and the `ModelIds` comment says so (task).
- Scout runs by hand, with no cache and no DOM hash (task, F4 AC2).
- Out of scope: using ground truth in the report, calling Scout from the runs API, caching, invalidation, a database table.
- Core is imported, never edited for shape, apart from the new schema. No new dependency. `Date.now()` is used for timestamps only (`docs/CONVENTIONS.md`).

## Design

### Core: `packages/core/src/ground-truth.ts`

```ts
/** One action of a path: the page it ran on, what it was, and the element it named. */
export const PathStep = z.object({
  url: HttpUrl,                       // the step's urlBefore, as observed
  action: ActionType,
  key: z.string().min(1).optional(),  // absent for scroll, back, wait
}).strict();

/** Every action an attempt ran, in order, and where the last one landed. */
export const ScoutPath = z.object({
  steps: z.array(PathStep).min(1),
  reachedUrl: z.url(),                // the last step's urlAfter: the page the goal was met on
}).strict();

export const ScoutAttempt = z.object({
  runId: RunId,                       // its run folder holds the evidence
  outcome: RunOutcome,
  path: ScoutPath.optional(),         // present exactly when outcome is success
}).strict().superRefine(/* path iff success */);

export const GroundTruth = z.object({
  taskId: TaskId,
  modelId: z.string().min(1),         // Scout's model
  startUrl: HttpUrl,                  // the URL every attempt passed to goto
  recordedAt: z.iso.datetime(),
  reached: z.boolean(),
  attempts: z.array(ScoutAttempt).min(1),
  shortest: z.object({ runId: RunId, path: ScoutPath }).strict().optional(),
  target: z.object({ key: z.string().min(1), page: HttpUrl }).strict().optional(),
}).strict().superRefine(/* below */);
```

`GroundTruth` refines, so the file stays consistent with itself:

1. `reached` holds exactly when some attempt succeeded.
2. Not reached means no attempt ended `error`. A crash is no evidence that a goal is out of reach.
3. `shortest` is present exactly when `reached`. Its `runId` names a successful attempt and its `path` equals that attempt's, compared as JSON. No successful attempt has fewer steps.
4. `target` is present exactly when the shortest path has a step with a `key`. It is the last such step, as `{ key, page: url }`.

The doc comment sets two conventions:

- **A hand-written fallback** (task, Notes for the reviewer) says `modelId: "hand"`, and its run ids are `run_hand-*`. Those ids name no folder, so week 4 can label the file hand-written rather than measured. It fits the schema as it is, since `RunId` accepts slugs.
- **`reached: false`** reads "Scout did not reach it in its attempts", never "unreachable".

Fixture `fixtures/ground-truth.json`, exported as `groundTruthFixture`. It covers the hard goal with three attempts: route B succeeds in 3 steps, route A in 2, and the third gives up. `shortest` is the route A attempt, and `target` is the "Order archive" link on `/deliveries`. Its keys are copied from the `fullObservation` of the `scout.browser.test.ts` runs, so they are the keys `collect` really gives.

`run.ts`: only the `ModelIds` comment changes. A Scout attempt is a run too, and there `actor` names Scout's model.

### Agent

`llm-actor.ts`: `llmActor({ settings, role?, llm? })`. `role` is `"actor" | "scout"` and defaults to `"actor"`. `settings.roles[role]` is the one source of everything role-bound: the backend's `modelId` and the role of every `complete`, which takes the temperature and effort from it. Nothing else changes.

`scout.ts`, exported as `@wayford/agent/scout` (originally the barrel; see the decision log, "(build)"):

```ts
export const SCOUT_PROFILE: Profile;  // prof_scout, label "Scout", desktop, no thresholds,
                                      // knownPatterns: every UI_PATTERNS entry, no caps, no dice,
                                      // budgetSeconds 3600
export const SCOUT_ATTEMPTS = 3;

export interface ScoutOptions {
  browser: Browser;
  task: Task;
  params: TargetAppParams;
  /** Writes `<dir>/<task id>.json`. Each attempt's run folder goes to `<dir>/attempts/<run id>/`. */
  dir: string;
  settings: LlmSettings;
  /** Replaces the adapter in tests, as in `llmActor`. */
  llm?: (logger: Logger) => Llm;
  logger: Logger;
  onEvent?: (event: RunEvent) => void;
}

export async function scout(options: ScoutOptions): Promise<GroundTruth>;
```

Flow:

1. Run attempts 1 to 3 one after another. Each is `runActor` with `SCOUT_PROFILE`, run seed `i`, `runsDir` `<dir>/attempts`, and the backend `llmActor({ settings, role: "scout", llm })`. When `runActor` rejects, `scout` rejects too. That happens before a run starts, or when folding the events or writing `result.json` fails. In the second case an attempt folder may already exist.
2. Each attempt's path comes from its `RunResult`. Take every step that is not wasted and has a `performedAction`. Each gives `{ url: urlBefore, action: type, key }`, where `key` is the key of the element in `fullObservation` whose `ref` the action named. `reachedUrl` is the last step's `urlAfter`.
3. Build the `GroundTruth`. `modelId` is `modelIds.actor` of the first result, which is the scout model, since `runStarted` records `backend.modelId`. `startUrl` comes from the first result. `shortest` is the first successful attempt with the fewest steps.
4. If nothing was reached and an attempt ended `error`, throw `WayfordError("scout_inconclusive")` and write no file.
5. `GroundTruth.parse` the result, `mkdir`, and write `<dir>/<task id>.json` with the same layout as `result.json`. Return it.

`run-scout.ts`, the package script `scout`: `pnpm --filter @wayford/agent scout`. Like `run-one.ts`, it loads the root `.env`, serves a build of the target app on 5174 and launches Chromium. It runs `scout` on both task fixtures with `TARGET_APP_DEFAULTS` and writes to the repository's `runs/ground-truth/`. For each task it prints every attempt (run id, outcome, path as `url —action key→`), then the file path. A task that fails, `scout_inconclusive` included, is printed, and the second task still runs, so a session on a real key is not lost. Exit 0 when both files are written, 1 when a setup or a task failed, and 2 on extra arguments.

### Guard: `actor-isolation.test.ts`

It copies the walker from `packages/filter/src/perceive-imports.test.ts`: the same import and export specifier regexes, `.js` to `.ts` resolution, and computed `import()` flagged. Three things change:

- **Entries.** Every non-test module in `src/` whose file name does not say Scout. That covers the barrel io loads, the loop, its backends and every by-hand command, so a new module is covered without an edit. This was revised in the build; see the decision log.
- **What is followed.** Relative specifiers, and `@wayford/agent` with its subpaths, resolved through the package's own `exports`. So `@wayford/agent/scout`, Scout's entry, is caught like a relative import. Any other package is a leaf.
- **What fails.** A reached module whose file name matches `/scout/i`. A reached module whose source matches `/ground[\s_-]?truth/i`: the directory, the schema or a comment about it. A computed `import()`. A relative import that resolves to nothing.

Tests:

1. No module outside Scout's reaches a Scout module or anything that names ground truth, and the walk really walked: it reached `llm.ts`, `act.ts` and `run-context.ts`.
2. The walker catches in-memory probes: an entry importing a module that imports `./scout.js`; an import of `@wayford/agent`, whose barrel exports `./scout.js`; a module reading `runs/ground-truth`; and `import { GroundTruth } from "@wayford/core"`.

## Decision log

| Question | Taken | Why |
|---|---|---|
| Do attempts emit `runStarted`? | Yes. They are runs through `runActor`, and the `ModelIds` comment says so. | Reuses the loop whole, which is the task's "the loop Scout reuses". The alternative needs a second walk without events. |
| Where do attempts' run folders go? | `<dir>/attempts/<run id>/` | All Scout output then sits in one directory, so it never mixes with Actor runs under `runs/`. |
| Ada's profile or Scout's own? | Scout's own, `prof_scout`, built in `scout.ts` | Ada is a persona under test, with a 120 s budget, and may change. A profile in `profiles/` would also join the persona grid and the banned Actor words. |
| How does Scout get role `scout`? | `llmActor` gains `role` | One parameter, against a second copy of the backend. The Actor default is unchanged. |
| Is the scout model required to be the one on the record? | `GroundTruth.modelId` comes from the attempts' `modelIds.actor` | It is the model that ran, as recorded, with no second source. |
| How many attempts, in what order? | Always 3, one after another, run seeds 1 to 3 | "Every successful attempt" and "the shortest" only mean something when several can succeed. Sequential runs keep the by-hand output readable. Distinct seeds will give distinct provider seeds once s2-10 lands. |
| What counts as "shortest"? | The fewest actions that ran. Wasted steps are excluded. The first attempt wins a tie. | A wasted step ran nothing. The tie rule keeps the choice deterministic. |
| Path URLs: full or paths? | Full URLs, as observed | They match `RunStep.urlBefore`, which the report will compare against. The tests compare pathnames. |
| What is the target? | The last element the shortest path acted on, and its page | For a URL goal that is the link that reached it: "Order archive" on `/deliveries`. |
| Nothing reached and an attempt crashed? | `scout_inconclusive`, no file. The schema refuses it too. | "No success is a result" holds for runs that finished. A crash claiming "unreachable" would mislead the report. |
| Who writes the file? | `scout()`, as `runActor` writes `result.json` | A week 4 caller gets the file without repeating the layout. |
| Commit the ground-truth files? | No. They are run output under the gitignored `/runs/`, and the PR carries the output. | The task's location. Committing them is the report's call in week 4. |
| Fields beyond the task's list | `startUrl`, `recordedAt`, `attempts[].runId` | A file says what setting and when, so it can be rerun when the app changes, and every path clicks through to its run (`AGENTS.md`, evidence). |
| Export `scout` from the barrel? | Yes, as the task says | The guard's entries are the Actor's own modules, and the barrel is followed when an Actor module imports it. |
| Export `scout` from the barrel? (build) | No. It ships as `@wayford/agent/scout`, as the fake adapter ships as `./fake`. | Cold review: io's runs import `runActor` from the barrel, so a barrel export would load Scout wherever the Actor runs, and the guard, which walks agent alone, would not see it. A subpath is still "from `@wayford/agent`", and the walker follows it. |
| Where does the guard start? (build) | From every non-test module in `src/` whose file name does not say Scout | PR review (Marcin): starting from the Actor's own modules left out the barrel. io loads the Actor through it, so a barrel export of `scout` passed the guard. The CLIs s2-11 added were left out too. |
| How is a tie checked? (build) | One function, core's `groundTruthOf(attempts)`, derives `reached`, `shortest` and `target`. Scout builds the file with it, the schema checks the stored fields against it, and a unit test pins the tie. | Cold review: a `<=` in place of `<` passed every test, and the schema accepted the later attempt. The simplify pass then found the rule written twice, in `scout.ts` and in the refine. |
| Share filter's walker? | Copy and adapt it | Test code cannot cross packages. A shared test package is more than an S task. |
| Budget on Scout's profile | 3600 s | `budgetSeconds` is required. The 20-step cap ends a lost attempt, and once s2-10 lands, B3 will not cut a slow model short. |
| Device | desktop | The demo device. A phone route differs only by the Menu toggle, and per-device ground truth is out of scope. |
| CLI duplicates `run-one.ts`'s serve and launch | Accept about 20 lines | s2-11 (PR #145) adds a third CLI. Extract the shared part once it merges (follow-up). |

## Risks

- A real Scout run on Luna at effort `max` could be slow, or could miss the faint link. The task's fallback is a hand-written file, which the schema accepts.
- s2-10 changes `runActor` (B3, provider seed, memory). The Scout profile has no memory cap and a long budget, so those parts leave it alone. But s2-10 also puts `actorSampling` on `runStarted`. If it reads the temperature from `settings.roles.actor`, every Scout attempt records the Actor's temperature beside Scout's model. s2-10 has to take the sampling from the backend, which reads `settings.roles[role]`. The PR flags this for s2-10.
- PR #145 (s2-11) touches `packages/agent/package.json`, and PR #148 (s1-03) touches `core/src/fixtures/index.ts`. Both conflicts would be one-line merges.
- The real-key box needs a key. The worktree has no `.env`, and this session cannot read the main checkout's. Main has no `run-scout.ts` until this branch merges, so the command runs in the worktree either way. Two ways to give it the key: the user exports the `LLM_*` variables in the shell, which `process.loadEnvFile` does not override, or links the main checkout's `.env` into the worktree root.
