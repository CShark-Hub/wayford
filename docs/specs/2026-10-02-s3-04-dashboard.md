# s3-04 — Dashboard and run detail: spec

Task: `tasks/s3-04-dashboard.md` · Branch: `feature/s3-04-dashboard` · Date: 2026-10-02
Status: approved 2026-10-02

## Goal

Every stored run can be found and replayed step by step with its evidence, video and trace, and a task's results read per persona at a glance.

## Constraints that bind

- **F7.** "Runs list filters by task, persona and outcome" (AC1), "Per task: success rate and median time per persona" (AC2), "step-by-step replay with screenshots, observation and action per step" (AC3), "Run header shows `persona | seed | run id`. The run id is the run's only number" (AC4). **F12 AC2**: video and trace "downloadable from run detail".
- **Task constraints.** Filters live in the URL. Stats "in Recharts, personas left to right in fixture order, Ada to Zoya". Header in monospace, plus the run's cost. Per step: the screenshot, "the Actor-facing text exactly as stored", the evidence ("every element with its state and decisions", so P1 to P4 masks, K1/K4 renames and A1 cuts each show with their rule), the action proposed and performed with dice rolls, and the narration "under a 'narration' label, set apart". A wasted step shows the latest earlier step's screenshot or none, the refused answers "labelled as refs the Actor was not shown" in place of the action, and their narrations "under the 'narration' label, never in the action slot".
- **Evidence and narration.** "Every verdict clickable through to evidence" (`AGENTS.md`). "The agent's narration is confabulated after the fact" (`AGENTS.md`, "Traps"): it is interpretation, never shown as measurement.
- **Contracts.** "Responses parsed with the core schemas. No run logic duplicated from core." `RunResult`, `RunStep` (complete, incomplete, wasted), `FullObservation`, `ObservedElement`, `ElementDecision`, `DiceRoll`, `Action`, `ActorResponse`, `Task` from `@wayford/core`. A step's `screenshotPath` is the screenshot taken after its action landed (`actionPerformed`, `packages/agent/src/actor-loop.ts` `land`).
- **Register.** "Output side is sober: monochrome, dense, evidence first, monospace for seeds and measurements" (`docs/PLAN.md` "UI"). The persona colour is the only accent. Function first: week 4's design pass decides the look (`tasks/BOARD.md`, week 3).
- **Stack and packages.** Recharts is the one chart library (`docs/STACK.md` "Web"). TanStack Router search params, TanStack Query. web imports core and talks to io over HTTP through the `/api` proxy. No dependency without a `docs/STACK.md` line. Files: `packages/web/**`, `pnpm-lock.yaml`.
- **s4-03** (merged as #144 after this spec was written). The routes come from `tasks/s4-03-runs-api.md`: `GET /runs?taskId&profileId&outcome`, `GET /runs/:id`, `GET /runs/:id/video`, `GET /runs/:id/trace`, `GET /runs/:id/steps/:index/screenshot`, `GET /tasks`. "Responses are core shapes."
- **Out of scope.** Findings and the report, the sweep, demo seed data (week 4). Starting runs (s3-03).

## Design

### Reaching io: `src/api/runs.ts`

Every io path and every response parse of this task lives in this one file, so a shape s4-03 settles differently is a one-file change.

```ts
/** `GET /api/runs`, parsed with `RunResult.array()`. Every stored run, newest first as io orders them. */
export async function fetchRuns(): Promise<RunResult[]>;
/** `GET /api/runs/:id`, parsed with `RunResult`; `null` on 404 (no run stored under that id). */
export async function fetchRun(id: string): Promise<RunResult | null>;
/** `GET /api/tasks`, parsed with `Task.array()`. Used for goal labels only. */
export async function fetchTasks(): Promise<Task[]>;

export const runsQuery: () => UseQueryOptions<RunResult[]>;          // key ["runs"]
export const runQuery: (id: string) => UseQueryOptions<RunResult | null>; // key ["runs", id]
export const tasksQuery: () => UseQueryOptions<Task[]>;              // key ["tasks"]

/** File routes, for `<img>`, `<video>` and the trace link. */
export function screenshotUrl(runId: RunId, stepIndex: number): string; // /api/runs/:id/steps/:i/screenshot
export function videoUrl(runId: RunId): string;                          // /api/runs/:id/video
export function traceUrl(runId: RunId): string;                          // /api/runs/:id/trace
```

`queryOptions` from TanStack Query, so a test seeds `queryClient.setQueryData(runsQuery().queryKey, runs)` and renders without a fetch. A non-OK answer throws `io answered <status>`, as `fetchHealth` does; a body that fails its schema throws with `z.prettifyError`, so the screen says io sent something that is not a run instead of drawing half of it. Path segments go through `encodeURIComponent`.

### The runs list URL: `src/runs/filter.ts`

| Param | Value | Absent or invalid means |
|---|---|---|
| `taskId` | `TaskId` | every task |
| `profileId` | `ProfileId` | every persona |
| `outcome` | `RunOutcome` | every outcome |

The names are io's `GET /runs` query names, so a dashboard URL's query reads the same as the API's.

```ts
export const RunsSearch = z.object({
  taskId: TaskId.optional().catch(undefined),
  profileId: ProfileId.optional().catch(undefined),
  outcome: RunOutcome.optional().catch(undefined),
});
export type RunFilter = z.infer<typeof RunsSearch>;
/** The runs every given key matches, in the order given. No key given keeps every run. */
export function filterRuns(runs: readonly RunResult[], filter: RunFilter): RunResult[];
```

Every key ends in `.catch(undefined)`, so a broken link degrades to "every" instead of an error screen, as `PreviewSearch` does. The screen fetches `GET /runs` once and filters in the browser: the per-task stats need every run of a task whatever the list shows, and a filter change then redraws without a request.

### Per-task results: `src/runs/stats.ts`

```ts
export type PersonaStats = {
  profileId: string;
  runs: number;          // every run of this persona on this task
  errors: number;        // outcome `error`: the tool fell over, not the persona
  successes: number;
  /** successes / (runs - errors); undefined when every run errored. */
  successRate: number | undefined;
  /** Median `durationMs` over the successful runs; undefined without a success. */
  medianSuccessMs: number | undefined;
};
export type TaskStats = { taskId: string; personas: PersonaStats[] };

/** Median of a list; the mean of the two middle values for an even count; undefined when empty. */
export function median(values: readonly number[]): number | undefined;
/**
 * One entry per task that has runs, by task id. Inside each, one entry per persona with runs on
 * that task: the ids in `personaOrder` first, in that order, then any other id, sorted.
 */
export function taskStats(runs: readonly RunResult[], personaOrder: readonly string[]): TaskStats[];
```

`personaOrder` is `bundledProfiles.map((p) => p.id)`: fixture order, Ada to Zoya, with Kai in place once `s1-04` adds his YAML. The stats take the task filter and ignore the persona and outcome filters: a success rate over runs already narrowed to one outcome is no rate, and cross-persona contrast is what the chart is for.

### Run detail URL and the replay: `src/runs/replay.ts`

```ts
export const RunDetailSearch = z.object({ step: StepIndex.optional().catch(undefined) });

/**
 * The step whose action left the page step `stepIndex` observed: the latest earlier step that is
 * not wasted (a wasted step ran nothing and left the page as it was). None when no such step exists
 * (step 0, or wasted steps from the start). A step's own `screenshotPath` is taken after its action
 * landed, so the returned step's screenshot, when it kept one, shows the observed page.
 */
export function observedFrom(steps: readonly RunStep[], stepIndex: number): RunStep | undefined;

/**
 * One line per action, an exhaustive switch over all seven `ACTION_TYPES`: `click e3`,
 * `doubleClick e2`, `type e4 "text"`, `scroll down`, `back`, `wait 500 ms`, `giveUp`.
 */
export function describeAction(action: Action): string;
```

Every step number in this task is a `stepIndex`, never an array position: `?step=N`, the `stepIndex` of the step `observedFrom` returns and the `:index` of the screenshot route. A step is found with `steps.find((s) => s.stepIndex === N)`, and "past the last" means no step has that index. `RunResult` does not promise the indices run 0 to n-1 without a gap.

### Screens

**`/runs`** (`src/screens/runs.tsx`, `validateSearch: RunsSearch`):

1. Header "Runs", with the number shown of the number stored.
2. Filters: three native `<select>`s, Task, Persona and Outcome, each with an "All" option. Options: tasks from `GET /tasks` (labelled by goal) plus any task id the runs carry; bundled personas in fixture order plus any other profile id the runs carry; `RUN_OUTCOMES`. A value the URL names that no option holds is added as an option, so the select always shows what the URL says. A change navigates with the key set, or removed for "All", pushing a history entry.
3. Results per task (`src/runs/task-results.tsx`): for each `TaskStats`, a heading with the goal (or the id), two Recharts `BarChart`s, success rate in percent and median time to success in seconds, one bar per persona in its persona colour, animation off, fixed size; and under them a table with the exact numbers: persona, runs, success (`3/9, 33%`), median time to success, errors. The table is what a screen reader and a test read; the chart is the glance.
   - A chart draws only the personas it has a value for: a persona whose runs all errored is left off the rate chart, and one with no success off the time chart, each named in a line under that chart ("No success: Vera, Zoya"; "Every run errored: Milo"). An empty place on the axis would read as 0% or as the fastest. The table says "all errored" and "no success" in those cells.
   - The persona, success and error cells link to their evidence (`AGENTS.md`, "Every verdict clickable through to evidence"): the persona cell to `/runs?taskId=<task>&profileId=<persona>`, the success count to the same with `&outcome=success`, the errors count with `&outcome=error`. The links reuse `RunsSearch`.
4. The run list: a table of the filtered runs, one row each: persona (colour dot and label), task, outcome, seed, duration, steps, cost in USD, and the run id in monospace as a link to `/runs/$runId`.
5. States: loading, an io error with its message, "No runs stored yet", and "No run matches these filters".

**`/runs/$runId`** (`src/screens/run-detail.tsx`, `validateSearch: RunDetailSearch`):

1. Header: `Vera | 424242 | run_vera-hard-1` in monospace (`persona label | seed | id`, the profile id when the persona is not bundled), then outcome, duration, cost (`$0.0201`, tokens in and out), task goal, Actor model id, start URL. `--persona` set on the root, as the preview does.
2. Recording: a `<video controls>` on `videoUrl` with a "Download video" link (`download`) beside it when `videoPath` is set, and a "Download trace" link (`download`) on `traceUrl` when `tracePath` is set; each says "not recorded" otherwise (F12 AC2).
3. Steps: an ordered list of links to `?step=k`, each with its index and `describeAction(performedAction)`, "wasted" or "stopped" in place of an action; the current one carries `aria-current="step"`. Previous and next links.
4. The step (`src/runs/step-replay.tsx`, `StepReplay({ run, step })`), five sections, each a `<section aria-labelledby>` with its own `<h3>`, in this order:
   - **Screenshots**: two figures side by side, so the image matches the evidence it sits beside. "Observed": `screenshotUrl(run.id, observedFrom(...).stepIndex)`, captioned "The page this step observed, as step K's action left it", or "No screenshot of the start page" at step 0 and when no earlier step has one. "After": the step's own `screenshotPath`, captioned "After this step's action", or, on a wasted step, "No action ran", on an incomplete one, "The run stopped before the action landed". The Actor's view and the Evidence describe the Observed page.
   - **Actor's view**: `step.actorObservationText` in a `<pre>`, exactly as stored, never re-rendered.
   - **Evidence**: the URL, title, `hiddenCount`, `belowFoldCount`; then one table row per element of `fullObservation.elements` in stored order: ref (or none), role, the real `name`, state, what the Actor read, the measured metrics, and every decision with its rule. "Actor read" comes from core's `toActorObservation(fullObservation)` matched by ref, so a masked or renamed name is core's projection, not a second one; an invisible element reads "not shown". Decisions print as `P1 contrast 2.1 < 3, rolled 0.42: degraded`, `V2 below`, `K1 <pattern>`, `A1`: a switch on `stage` that prints `rule` from the data, so K2 and A3 show when `s1-03` and `s1-05` emit them.
   - **Action**: complete: proposed, performed, and the dice as a table (rule, p, rolled, fired), "No dice rolled" when `[]`; step cost. Wasted: heading "Refs the Actor was not shown", one `describeAction` line per refused answer, no narration in it. Incomplete: the planned action and "never landed", or "The run stopped before an action was planned".
   - **Narration**: heading "Narration", a line that it is the model's own account, written as it answered, interpretation and not measurement. A complete or incomplete step: `step.narration`, or "No narration" (Jev writes none). A wasted step: each refused answer's narration, labelled "Answer 1, not shown: click e3".
5. States: loading, an io error, "No run <id> is stored. A run is stored when it ends", and for a `step` past the last, "This run has no step N" above the step list.

**Shell and router.** `src/router.tsx` adds `runsRoute` and `runDetailRoute`; `src/shell.tsx` adds a "Runs" link between Preview and Events.

### Data flow

`GET /api/runs` → `RunResult.array()` → `filterRuns(runs, search)` → list; `taskStats(runs with the task filter, bundled order)` → charts and tables. `GET /api/runs/:id` → `RunResult` → header, recording, step list, `StepReplay(step = search.step ?? 0)`. Screenshots, video and trace are plain URLs the browser fetches itself.

## Risks

- **s4-03's real shapes or names differ** (an envelope, other query names, another screenshot path). Confined to `src/api/runs.ts` and `RunsSearch`; the `pnpm dev` box catches it after s4-03 merges. Resolved: s4-03 merged (#144) with the routes, query names and bare core shapes assumed here.
- **Payload.** `GET /runs` carries every step's full observation. Fine for tens of runs; F11's 60 runs may be several MB. A summary endpoint is week 4's if it bites.
- **Recharts in a static render** may emit an empty SVG or warn. Tests assert the table, not the chart's internals.
- **Kai lands mid-task** (`s1-04`). Order comes from the bundled YAML, so he takes his place without code.
