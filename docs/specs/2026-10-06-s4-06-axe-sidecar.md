# s4-06 — axe-core sidecar: spec

Task: `tasks/s4-06-axe-sidecar.md` · Branch: `feature/s4-06-axe-sidecar` · Date: 2026-10-06
Status: approved 2026-10-06

## Goal

io scans each target-app page with axe-core once per page and app parameters, stores the result, serves it, and the preview shows the current page's violation count on a card. The report cites each violation on a page its runs visited as a `measurement` finding.

## Constraints that bind

- **The task's Constraints:**
  - axe is a measurement, never a filter input: nothing in `packages/filter` reads it, and the Actor never sees it;
  - rules limited to the WCAG 2.2 A and AA tags, so the card's claim is exactly what was checked;
  - the scan is by page, not by run: the pages are the same for every persona at fixed app parameters (F10, simplified 2026-10-04);
  - a failed scan shows "axe did not run" on the card, never "0 violations".
- **The task's Out of scope:** no scanning during runs, no pages outside the target app, no RULES calibration check against axe.
- **F10:** AC1 axe violations stored per target-app page, scanned once per page and app parameters. AC2 the report can cite one as a `measurement` finding.
- **F8:** AC1 every finding has its type. AC2 every finding links to at least one evidence step: no evidence, no finding. AC3 every finding has a recommendation.
- **`Finding` in core:** `axeRuleId` is allowed on a `measurement` or `deterministic` finding only. `basis` may be empty on a measurement, and so may `personaIds`: "a measurement holds whoever is looking".
- **s4-04's handover** (its spec, decision log, "axe `measurement` findings"): "s4-06 widens `Draft` to join the same call". Code writes the finding, and the Analyst writes only its recommendation.
- **io's barrel** loads neither agent's runtime nor Playwright (s4-03, "The barrel"). Like `live-measure.ts` and `chromium.ts`, the scanner stays out of it. Only `server.ts` and the `analyse` CLI import it.
- **`docs/STACK.md`:** `axe-core` injected through `@axe-core/playwright`. Pick a mature version (pnpm's release-age policy).
- **`docs/CONVENTIONS.md`:** the database pattern is one JSON document per row, with real columns only for what a query filters or sorts on. A new shape gets a fixture in core in the same PR. `Date.now()` never drives a decision.

## Design

### 1. Core: `AxeScan` (`packages/core/src/axe.ts`, at rest)

`AxeScan` is a record at rest that io stores and serves and web parses, so it lives in core, as `Sweep` does. It sits beside the seven contracts and changes none of them.

```ts
/**
 * The axe-core tags a scan runs: WCAG 2.0, 2.1 and 2.2 at levels A and AA, as axe-core 4.13 names
 * them (its API.md, "Axe-core Tags"). axe has no `wcag22a` tag: no WCAG 2.2 level A criterion has
 * a rule. The card's words, "WCAG 2.2 A and AA", say exactly this set.
 */
export const AXE_WCAG_TAGS = ["wcag2a", "wcag2aa", "wcag21a", "wcag21aa", "wcag22aa"] as const;

export const AXE_IMPACTS = ["minor", "moderate", "serious", "critical"] as const;

/** One rule axe-core found violated on the page. */
export const AxeViolation = z.object({
  ruleId: z.string().trim().min(1),           // axe's rule id, e.g. "color-contrast"
  impact: z.enum(AXE_IMPACTS).nullable(),     // axe types it nullable; violations carry one in practice
  tags: z.array(z.string().trim().min(1)),    // the rule's WCAG tags, those starting "wcag", in axe's order
  help: z.string().trim().min(1),             // axe's one-line help, for the report's title and fallback
  nodes: z.number().int().positive(),         // how many elements violate it
}).strict();

/** One target-app page at one set of app parameters, scanned once. */
export const AxeScan = z.object({
  url: AxeUrl,            // the key: the page's path and the app's query, "/settings/data?contrast=2&fontPx=16&targetPx=36"
  scannedAt: z.iso.datetime(),
  axeVersion: z.string().trim().min(1),       // axe-core's own `testEngine.version`
  violations: z.array(AxeViolation),
}).strict();
```

`AxeUrl` is a string that starts with `/`, and it has a query and no hash. It carries no origin: the same build serves the target app on 5174, on a test's free port and in the `analyse` CLI, and a stored scan holds for all three.

Fixture: `axe-scans.json`, with two scans taken from a real run of the scanner at the target app's defaults: `/deliveries` with its `color-contrast` violation (the archive link at 2.005:1), and `/settings/data` as it actually scans. `axeScanFixtures: AxeScan[]` in `fixtures/index.ts`. A test in `axe.test.ts` parses it and refuses a URL with an origin, a hash or no query.

### 2. io: storage (`db/schema.ts`, `db/axe.ts`, migration `0005_axe_results`)

```ts
export const axeResults = sqliteTable("axe_results", {
  url: text("url").primaryKey(),
  document: text("document", { mode: "json" }).$type<AxeScan>().notNull(),
});
```

Only the key is lifted out. When it was scanned, and everything else the task lists, stays in the document: nothing filters or sorts on them (`docs/CONVENTIONS.md`). `db/axe.ts` provides `saveAxeScan(db, scan)`, an insert that replaces on conflict, and `loadAxeScan(db, url): AxeScan | undefined`. Both parse with `parseRow`, as `db/sweeps.ts` does. The migration is generated by `db:generate --name axe_results`.

A stored scan is kept until it is cleared, and nothing clears it on its own: a change to the target app or an axe upgrade keeps serving the old scan. To scan again, run `DELETE FROM axe_results` on the database `DATABASE_URL` names. The next request then scans afresh. `db/axe.ts`'s comment says so.

### 3. io: scanned once (`packages/io/src/axe.ts`, barrel-safe)

```ts
/** Scans one target-app URL (an `AxeUrl`). Every failure it knows is a `WayfordError`. */
export type AxeScanFn = (url: string) => Promise<AxeScan>;

/** The stored scan of `url`, or a fresh one, stored, on a miss. */
export type AxeLookup = (url: string) => Promise<AxeScan>;

/** `page` at the app's query: `axeUrl("/deliveries", "?contrast=2&fontPx=16&targetPx=36")`. */
export function axeUrl(page: string, search: string): string;

export function axeLookup({ db, scan }: { db: Db; scan: AxeScanFn }): AxeLookup;
```

`axeLookup` reads the database first. On a miss it calls `scan`, saves the scan and returns it. Like `measureRoute`, it holds an in-flight map from URL to promise, so the route and the Analyst share one scan when they ask together. A rejected promise is dropped and never stored, so a target app started later gets scanned on the next request.

### 4. io: the scanner (`packages/io/src/axe-scan.ts`, outside the barrel)

```ts
export function axeScanner({ browser, origin }: { browser: SharedBrowser; origin: string }): AxeScanFn;
/** For the `analyse` CLI: on its first scan, serves the target app's build and launches Chromium. */
export function servedAxeScanner(): { scan: AxeScanFn; close(): Promise<void> };
```

Each scan works like this:

1. It checks the URL first and throws `WayfordError("invalid_axe_url")` when the path is not in `TARGET_APP_PATHS`, or when the query is not the app's three parameters spelled as `startUrlFor` spells them. It builds the page URL with `startUrlFor({ startUrl: origin + path }, params)` and checks that this equals `origin + url`. So a scan only ever opens a target-app page at valid parameters.
2. It opens a context of its own on the shared browser with `deviceContextOptions("desktop")`, loads the page and awaits its fonts. Both steps are `live-measure.ts`'s, which now exports them as one `withOwnContext`: the context under its deadline, the page opened in it (simplify). The caller names its work, `measuring` or `scanning`, so a failed scan says "while scanning /x", never "measuring". Measuring behaves and words its errors as before.
3. It runs `new AxeBuilder({ page }).withTags([...AXE_WCAG_TAGS]).analyze()`. It keeps `violations` only, and maps each to `AxeViolation`: the node count, and the tags filtered to `/^wcag/`. It records `testEngine.version` and the time.
4. A deadline covers the whole scan. Failures become `WayfordError`s, as in `live-measure.ts`: `target_app_unavailable`, `page_not_settled`, `font_failed`, `browser_failed`, and `axe_failed` for an error axe itself throws.

`servedAxeScanner` is the `analyse` CLI's scanner. The CLI walks a build it serves on a free port, so it must not depend on a `pnpm dev` it does not start. On the first scan it serves the build (`serveTargetApp()`) and launches Chromium through `sharedBrowser()`, and `close()` stops both. A build or serve that fails becomes `target_app_unavailable`, and a failed launch is `sharedBrowser`'s own `browser_launch_failed`. Both are `WayfordError`s, so in a report they cost only the axe findings (§6, step 3), never the Analyst call. A failed serve is not kept: the next scan tries again.

### 5. io: `GET /axe?page=<path>` (`routes/axe.ts`)

- 200 `AxeScan`: the page at the app's defaults (`TARGET_APP_DEFAULT_QUERY`), as stored, or scanned on a miss and then stored.
- 400 `{ error }`: `page` is missing, not in `TARGET_APP_PATHS`, or repeated, or the query has an unknown key. Nothing is scanned.
- 502 `{ error }`: the scan failed with a `WayfordError`. Nothing is stored.

The query schema follows `MeasureQuery`, with `page` required.

`createApp` takes `scanAxe: AxeScanFn` in `AppOptions` and builds one `axe = axeLookup({ db, scan: scanAxe })`. It hands `axe` to `/axe` and to `/reports`, whose `AnalystDeps` gains `axe: AxeLookup`. `server.ts` wires `axeScanner({ browser, origin: TARGET_APP_ORIGIN })` on the one shared Chromium. `test-app.ts` gives `testApp` a default `scanAxe` that answers a scan with no violations, and gives the Analyst's tests an `axe` of their choosing.

### 6. io: axe findings in the report (`analyst-axe.ts`, `analyst.ts`, `analyst-closures.ts`, `analyst-digest.ts`, `analyst-prompt.md`)

`Draft` is widened: its `closing: RouteClosed` becomes `fallback: string`, the recommendation code writes when the Analyst leaves one blank. `closureFindings` fills it with `fallbackRecommendation(first)`, so its output and tests are unchanged in substance.

`analyst-axe.ts`:

```ts
export async function axeDrafts(input: {
  taskId: TaskId;
  runs: readonly RunResult[];   // the chosen runs, in the report's order
  axe: AxeLookup;
  logger: Logger;
}): Promise<Omit<Draft, "key">[]>;
```

1. Only runs on the target app count. A run counts when its `startUrl`'s host is `localhost` or `127.0.0.1`, the only place the target app is served. Every run's start URL carries the app's three parameters, whatever the task (`actor-loop.ts`, `startUrlFor`), so the parameters alone would let a public-site run (s4-08) scan the target app's `/` and cite it against the site's home page. Within a counted run, only a step whose `urlBefore` has the run's own origin counts. Each counted step stood on its page, the path of its `urlBefore`, at the app parameters of its run, the query of the run's `startUrl`, so its URL is `axeUrl(path, search)`. Steps on a path outside `TARGET_APP_PATHS` are skipped. URLs are taken in the order a step first stood on them, runs in the report's order.
2. A URL's evidence is the first step of each run that stood on it, by run and then by step. That gives one step per run that saw the page, not every step on it.
3. `await axe(url)`, one URL at a time. A `WayfordError` is logged as a warning naming the URL and its code, and that URL gives no findings: the report is still built. Any other error propagates, since it is a bug.
4. Each violation becomes one finding draft:
   - `type: "measurement"`, `axeRuleId: violation.ruleId`, `basis: []`, `personaIds: []`;
   - title: `axe-core: <help> (<ruleId>) on <path>`;
   - detail: `axe-core <version> reports <ruleId> on <path>, scanned on desktop at the app's <query>: <n> elements, impact <impact>, WCAG tags <tags>. <k> of the report's runs stood on the page.` A null impact reads `impact not given`. "On desktop" is said because the evidence can be a phone persona's steps (Milo), and a rule such as `target-size` can read otherwise at a phone's width;
   - fallback: `Fix what axe-core's <ruleId> rule reports on <path>: <help>.`

In `analyseTask`, the axe drafts are listed before the closure drafts and keyed `d1…` across both, so the answer still names every draft once. The report's findings come out measurement first, then deterministic by persona, then hypotheses. That is PLAN's order, "measurement / deterministic / hypothesis". The blank-recommendation fallback reads `draft.fallback`, and its warning names the draft's key and title in place of the route id.

`analyst-digest.ts`: a draft with no persona is listed as `d1, axe-core measurement on the page: <title>`, and an empty basis reads `rules: none`. `analyst-prompt.md` gains one clause: an axe-core measurement concerns the page, not one persona, and rests on no rule of the listed findings.

### 7. web: the card (`api/axe.ts`, `screens/preview.tsx`)

`api/axe.ts` mirrors `api/measure.ts`. `fetchAxeScan(page)` calls `GET /api/axe?page=…` and parses the answer with `AxeScan`. A non-OK answer rejects with io's `error`, or with the HTTP status when io sent none. `axeQuery(page)` keys on `["axe", page]` with `staleTime` and `gcTime` infinite and no retry, as `measurementQuery` does: io keeps the scan, so a slider move asks nothing.

`AxeCard` in the stage, beside the page picker row, above the drawn page, keyed by `state.page` alone, since the scan does not depend on the persona or the device:

- pending: `axe-core is scanning <page>…`, as plain text with no `role="status"`. The stage's one status line stays its measurement's, which `preview.test.tsx` reads as the first `role="status"` on the page;
- error: **axe did not run** on `<page>`, with io's reason under it. Never a count;
- success: **axe-core, WCAG 2.2 A and AA: N violations** (`1 violation`, `0 violations`), the rule ids as a list, each with its element count (`color-contrast, 1 element`), and a muted line: `Scanned once per page on desktop, at the target app's default parameters.`

The card uses the shell's existing tokens (`rounded-lg border bg-card`). The look is s3-11's.

## Decision log

| Question | Taken | Why |
|---|---|---|
| Where the scan's shape lives | Core, `axe.ts`, with a fixture | io stores and serves it and web parses it. A second copy in web would drift. `Sweep` set the precedent of a record at rest beside the seven contracts |
| The key | Path plus the app's query, with no origin (`/deliveries?contrast=2&fontPx=16&targetPx=36`) | "Once per page and app parameters". One build serves the app on any origin, and the CLI's free port must find what `pnpm dev` stored |
| Which device the scan runs on | Desktop only | "By page, not by run", and the card is the same for every persona. A per-device scan would be a second dimension the task does not ask for. The card says "on desktop" |
| What is stored per violation | Rule id, impact, WCAG tags, node count, axe's help line. Plus axe's version and the time per scan | The task's list, plus `help` for the finding's title and fallback, and the version as provenance. `incomplete` and `passes` are not stored: the card claims violations only |
| Which tags | `wcag2a`, `wcag2aa`, `wcag21a`, `wcag21aa`, `wcag22aa` | All A and AA through 2.2, as axe 4.13 names them. It has no `wcag22a` tag, and adding a tag it does not define would only hide the mismatch |
| `page` on `GET /axe` | Required | The card always knows its page. A default would answer a question nobody asked |
| How the Analyst gets scans | Through the same `AxeLookup` the route uses, so it scans on a miss | A report must not depend on whether someone opened the preview first. One in-flight map serves both |
| A scan that fails during a report | Logged as a warning; that page gives no axe finding; the report is still built | The report's own numbers do not depend on axe, and a failed sidecar must not cost the Analyst call. Recording it on the `Report` would change its contract, which is outside this task |
| A finding's evidence | The first step of each run that stood on the page | "Steps that stood on that page", kept to one per run. Every step on the page would list hundreds and say nothing more |
| A finding's `personaIds` and `basis` | Both empty | `Finding`: "a measurement holds whoever is looking". No rule of `RULES.md` produced it |
| How `Draft` widens | `closing` becomes `fallback: string` | s4-04 left the widening to this task. The fallback is the only thing `analyst.ts` read off the closing |
| Finding order | Measurement, then deterministic, then hypothesis | PLAN's order. Draft keys follow it |
| How the CLI scans | `servedAxeScanner`: it serves the build and launches Chromium on its first miss | The CLI already serves its own build for the walk and must not depend on `pnpm dev`. When every scan is stored, it starts nothing |

| `@axe-core/playwright` version | `^4.13.0` (2026-08-11), which brings `axe-core` ~4.13.0 | The current stable release, well past pnpm's release-age window |
| Where the card sits | In the stage, above the drawn page | Beat 3 points at the page and the card together. s3-11 restyles it |
| Which runs the axe findings read | Runs whose start URL is on `localhost` or `127.0.0.1`, steps on the run's own origin | Every start URL carries the app's parameters, so they cannot tell the target app apart.
